# 阶段复盘：插件系统架构与余额监控插件

**日期**：2026-09-19
**阶段**：v0.7.0 后规划期
**主题**：插件系统基础设施补全 + 第一个完整插件（余额监控）设计

---

## 一、背景

v0.6.0 已完成插件系统的逻辑扩展层（9个生命周期钩子 + 7种SPI），v0.7.0 完成了学习型路由和省钱看板。但插件系统存在一个关键缺口：**只有逻辑扩展点，没有 UI 扩展点和配置扩展点**。

本次讨论围绕"第一个完整插件——余额监控与额度预警"展开，在设计过程中深入探讨了插件系统的架构完整性问题，并最终形成了"先补全基础设施，再做第一个插件"的共识。

---

## 二、核心讨论与决策

### 2.1 余额监控插件方案初版

最初输出的方案包含：
- 核心功能：余额同步引擎、预警引擎（4级预警）、路由感知
- UI展示：独立余额看板页面、首页总览卡片、账号卡片余额标识、日志详情预警信息
- 配置：10项可配置参数
- 数据模型：复用 ModelAccount 余额字段 + 新增 BalanceSyncLog / BalanceAlertLog 表

### 2.2 关键问题：插件是否需要改主程序？

**问题提出**：用户质疑方案中"可视化部分需要改主程序代码"，询问是不是每个插件都要改主程序。

**深入分析**：
- 当前插件系统的9个钩子全部是"请求管线内的钩子"，管不到管理后台的页面渲染
- 管理后台（admin.py）是独立的 NiceGUI 应用，页面、路由、组件都是硬编码的
- 插件系统目前没有提供：UI组件注入钩子、页面路由注册机制、导航菜单扩展点

**分类结论**：
| 插件类型 | 是否改主程序 | 占比 |
|---|---|---|
| 纯逻辑插件（安全审核/自定义分类器/选号器/限流等） | ❌ 不需要 | 70% |
| 需要配置但不需要UI的插件 | ⚠️ 少量（统一配置页做一次） | 20% |
| 需要UI展示的插件（余额监控/成本分析等） | ✅ 需要 | 10% |

### 2.3 架构决策：UI扩展点本来就应该有

**关键认知转变**：
- 最初建议"先做纯插件核心功能，UI放后面"——这是工程师的保守思维
- 从**架构逻辑**角度，UI扩展点是插件系统的固有组成部分，缺了它插件系统就是"瘸腿"的
- 从**技术债**角度，现在不做UI扩展点，以后每个需要UI的插件都要改主程序，主程序会被"污染"，再也拆不出来
- 从**生态角度**，社区开发者发现"写插件还要改主程序源码"，不会贡献插件

**决策**：先补全插件系统基础设施（UI扩展点 + 配置扩展点），再做第一个插件。

### 2.4 插件系统基础设施补全方案

#### UI扩展点（4个）

| 扩展点 | 能力 | SDK API |
|---|---|---|
| 页面路由注入 | 插件注册独立管理后台页面 | `register_page(route, title, render_func)` |
| 导航菜单扩展 | 插件在导航栏添加菜单项 | `register_nav_item(label, route, icon)` |
| 组件挂载点 | 插件在已有页面指定位置注入组件 | `register_component(hook_point, render_func, priority)` |
| 配置界面注入 | 插件注册配置表单，统一页面展示保存 | `register_config(schema, default, on_save)` |

**预设组件挂载点**：
- `dashboard.widgets`：首页小部件区
- `account.card.footer`：每个账号卡片底部
- `log.detail.extra`：每条日志详情底部
- `config.page.extra`：系统配置页底部

#### 配置扩展点

- 存储：复用 SystemConfig 表，新增 `plugin_configs` JSON 字段
- 读取：`get_plugin_config(plugin_name) -> dict`
- 保存：`set_plugin_config(plugin_name, config)`
- 优先级：环境变量 > 数据库配置 > 默认值

### 2.5 余额监控插件完整方案（基于补全后的基础设施）

#### 核心功能

**1. 余额同步引擎**
- 触发时机：每日首次请求、请求完成后节流同步、疑似耗尽立即同步、定时全量同步、手动触发
- BalanceProvider SPI：可扩展的厂商余额查询接口
- 内置Provider：Kimi、DeepSeek、SiliconFlow（迁移现有 balance.py）、Manual（兜底）
- 容错：单账号节流（10分钟）、并发限制（3个）、失败退避、超时控制（20秒）

**2. 预警引擎**
- 4级预警：🟢正常 / 🟡注意 / 🟠警告 / 🔴紧急 / ⚫耗尽
- 阈值可配置：金额（警告¥1.0/紧急¥0.3）、Token（警告10万/紧急3万）
- 耗尽预测：基于近7天日均消耗速度预测耗尽时间

**3. 路由感知**
- `route.before` 钩子：过滤已耗尽账号、紧急账号降权
- 不替换现有选号器，只做预处理

#### UI展示（通过4个扩展点注入）

| 展示内容 | 使用的扩展点 |
|---|---|
| 独立余额看板页面 `/admin/balance` | 页面路由注入 + 导航菜单扩展 |
| 首页余额总览卡片 | 组件挂载点 `dashboard.widgets` |
| 账号卡片余额标识 | 组件挂载点 `account.card.footer` |
| 日志详情预警信息 | 组件挂载点 `log.detail.extra` |

#### 配置（10项）
同步间隔、同步节流、最大并发、警告/紧急阈值（金额+Token）、路由感知开关、耗尽过滤开关、紧急降权开关

#### 数据模型
- 复用：ModelAccount 余额字段（balance_remaining/balance_unit/balance_sync_date/daily_used_*）
- 新增：BalanceSyncLog（同步日志）、BalanceAlertLog（预警日志）

### 2.6 插件开发指南 + Hello World 示例

**明确两个不同的东西**：
- 插件开发指南：文档（Markdown），教开发者如何写插件
- Hello World 插件：真实可运行的插件（Python），加载后能真正在 WoolGate 里跑起来

**Hello World 插件演示内容**：
- 注册组件到 `dashboard.widgets`（首页显示 Hello World 卡片）
- 注册组件到 `log.detail.extra`（日志详情显示插件信息）
- 注册 `request.started` 钩子（请求开始时打印日志）
- 注册独立页面 `/hello-world` + 导航菜单项
- 注册配置（可修改显示消息）

## 三、实施顺序

```
第一步：插件化基础设施（架构层面）
   ├─ 插件 SDK 扩展（4个注册表 + register API）
   ├─ 主程序接入页面路由注入和导航菜单扩展
   ├─ 主程序添加4个组件挂载点
   ├─ 主程序新增统一插件配置页面
   └─ 配置读写函数实现
   ↓ 用 Hello World 插件验证基础设施可用
第二步：余额监控插件（第一个完整插件）
   ├─ BalanceProvider SPI + 4个内置 Provider
   ├─ 余额同步引擎 + 3个钩子
   ├─ 预警引擎（4级预警 + 耗尽预测）
   ├─ 路由感知（route.before 钩子）
   ├─ BalanceSyncLog / BalanceAlertLog 表
   ├─ UI：独立页面 + 首页卡片 + 账号标识 + 日志详情
   └─ 配置界面
第三步：插件开发指南 + Hello World 示例
第四步：全量验证
```

## 四、关键经验与教训

### 4.1 架构完整性优先于功能交付

第一个插件的设计过程暴露了插件系统的架构缺口（UI扩展点缺失）。正确的做法是**先补全基础设施，再做具体插件**，而不是用"改主程序"的方式绕过架构问题。技术债的利息是复利的，越晚还成本越高。

### 4.2 第一个插件是"样板间"

第一个插件展示的是插件系统的**完整能力天花板**。如果第一个插件只能改逻辑不能改UI，插件系统的定位就被锁死在"逻辑钩子"层面。第一个插件必须完整使用所有扩展点，验证"逻辑+UI+配置"的全链路插件化能力。

### 4.3 基础设施做一次，所有插件受益

UI扩展点是基础设施，做一次，所有未来的插件都能用。现在是做的最佳时机——还没有任何插件依赖"改主程序"的方式，没有历史包袱。

### 4.4 文档与示例同等重要

插件开发指南（文档）+ Hello World（实物样品）是吸引社区开发者的关键。开发者看完说明书，直接把 Hello World 加载进去看效果，然后改几行代码变成自己的插件——这是最低的参与门槛。
